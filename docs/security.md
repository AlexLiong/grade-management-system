# 安全设计、威胁分析与应急处理

## 安全目标与信任边界

保护成绩机密性、成绩与状态完整性、操作主体真实性、可追溯性和基本可用性。浏览器、网关、业务服务、数据服务、审计账本、链工具分别是边界。普通用户不接触内部 RPC、数据库账号或审计密钥。

|威胁|具体防护|限制|
|---|---|---|
|弱口令/数据库密码泄漏|BCrypt cost 12；随机初始密码；改密要求 12–72 位含字母数字|未实现 MFA、密码泄漏字典检查|
|窃取 Cookie|HTTPS、HttpOnly 会话、Secure、SameSite=Strict、2 小时失效|本机管理员仍能获取进程或文件数据|
|跨站请求伪造|双端同源策略、会话绑定 CSRF token、POST 必须匹配|登录不要求既有 CSRF，但网关限制 Origin|
|水平越权|教师课程归属、学生选课与本人过滤、只展示已提交成绩|信任已认证业务服务生成的内部领域请求|
|垂直越权|角色权限交集、服务端逐项检查、停用即拒绝、权限变更撤销会话|未实现细化至每门课程的自定义授权表|
|SQL 注入|表列白名单、操作枚举、PreparedStatement、类型转换|内部白名单仍需代码审查|
|存储型 XSS|Vue 文本绑定、不使用 v-html、CSP 禁止内联脚本|允许 style 内联及仅 WebAssembly 编译，便于图表/OCR|
|内部请求伪造/重放|独立调用者密钥、HMAC、30 秒时间窗、nonce 缓存|多副本全局重放缓存和独立机器时钟同步为生产扩展|
|注册中心 SSRF|https、域名白名单、服务身份一致、拒绝 userinfo/query/fragment|需由运维维护 SERVICE_HOSTS|
|数据库直接改分|AES-GCM 绑定主键、学生、课程、状态、版本|修改整条旧密文可回放，但独立账本可识别版本回退|
|数据库删除或伪造成绩|账本原始快照核对、扫描未审计主键|当前单次未审计主键扫描上限 10000，扩大业务需分页|
|账本篡改/截断|前序哈希、HMAC、AES-GCM、EVM 交易数量和 input 校验|同机所有密钥和链目录同时失守无法保证可信|
|审计网络中断|事务发件箱、重复事件去重、后续写入失败关闭|提交事务与链锚定不具备跨系统原子性|
|暴力登录|每账号五次失败锁定五分钟|需在正式网关补充全局/IP 限流和验证码，防随机账号资源耗尽|
|选课越权与抢课|`SELECTION_ADMIN` 与 `SELECTION_ENROLL` 分离、服务端校验窗口/范围/开关、写操作进审计|未实现选课并发配额、候补队列与分布式锁|
|选课关系被伪造或抹除|`enrollments(course_id,student_id)` 唯一索引、`enrollment_records` 只增流水、`SELECTION_*` 审计动作|批量与结算依赖单事务，跨批次并发未做全局串行化|
|组织层级被越权维护|`ORG_ADMIN` 独立授权、删除前校验课程与账号引用、级联需 `force` 确认|未按学院划分管理员数据域，持权管理员可跨学院维护|
|OCR 隐私泄漏|模型与 WASM 本地、原图在浏览器识别、处理后终止 worker、撤销 blob URL|识别文本需人工确认，浏览器自身内存不提供物理安全擦除保证|

## 密钥与密码

`setup.mjs` 使用系统 CSPRNG 生成密钥和初始密码。`.runtime` 目录权限为 0700，配置/私钥为 0600（Windows 需使用 NTFS ACL 限制服务用户）。该目录被 Git 忽略，交付源码压缩包应排除全部 `.runtime`。

开发机器为了直接启动，各服务读取同一个随机配置文件。此便利模式不能当作生产秘密隔离：分布式部署时仅把本服务需要的调用验证密钥与加密密钥放进该服务运行环境，使用 KMS/Vault 或秘密挂载。数据 RPC 签名和成绩加密当前共用 `DATA_KEY`，生产应拆成不同用途的密钥并加入密钥版本，迁移旧密文后再轮换。

密钥丢失意味着无法解密历史成绩或账本，不能通过重建配置解决。备份密钥必须与数据备份分开、加密保管，并验证恢复流程。源码和报告不包含随机密码。

## 数据加密和原始证据

成绩载荷以 `base64(iv):base64(ciphertext+tag)` 保存；AAD 为 `id|course_id|student_id|state|version`。变更状态会重新加密，不能只更新状态列绕过审计。数据库发件箱同样加密，审计服务再次使用独立密钥加密快照，链上只记录不可逆摘要。

管理员核查从独立账本获取最终合法状态，再与业务库比较。数据库行缺失、密文认证失败、状态/版本变化、已删除记录重新出现、未审计新行都会形成异常。管理员可读到维护前后原始分数，但系统不会自动覆盖数据库，以免把调查变成新的无授权修改。

`SEED` 是唯一允许在链未就绪时初始化的敏感批次，仍在数据库事务中记录发件箱，后续同步；正式部署关闭演示初始化，并用受控管理流程创建首个管理员。

### 演示重建会清空账本与链锚点

`SchemaCatalog.SCHEMA_VERSION` 变化触发的整库重建会连带清空独立账本与 EVM 锚点：`DemoInitializer` 调用审计服务的重置接口，`LedgerService.reset()` 先请求 chain-worker 的 `POST /reset` 清空锚点，再截断并重写账本文件，随后重新灌入数据并重新锚定。

这意味着**本机演示环境下账本可以被合法重置**，因此不能宣称「本机管理员无法清空账本」：可重置性是重建流程的必要条件，而不是安全边界。`POST /reset` 在 chain-worker 中没有任何业务鉴权，只靠内部 HMAC 与回环地址保护，生产部署必须删除或关闭该端点；同理，生产库不得开启整库重建开关。审计的不可静默改写承诺仍成立：任何一次运行期内的账本修改或不完整重建都会在 `/integrity` 与链校验中暴露，只有「按流程重建」这一条合法路径会同时丢弃数据库与账本。

## 多管理员授权

实现或签语义：任意启用且持 `GRADE_ADMIN` 的管理员均能执行撤销，记录具体操作者。不存在两个管理员共同批准才可修改的“双签”功能，不将两者混称。权限变更记录快照，禁止管理员停用自己或移除自己的人员管理权限。账户角色建立后不允许直接转换。

## 组织与选课的权限模型

组织管理与选课沿用「角色给权限集合、服务端逐项断言」的 RBAC，不引入新角色。`Models.PERMISSIONS` 中：

|角色|新增权限|说明|
|---|---|---|
|ADMIN|`ORG_ADMIN`|学院、专业、班级的查询与维护，人员归属调整|
|ADMIN|`SELECTION_ADMIN`|选课批次发布/关闭/取消/结算、批量选课、查看选课记录|
|STUDENT|`SELECTION_ENROLL`|查看可选批次、选课、退课、查看本人选课|

权限判定发生在三处，缺一不可：`ApiController` 完成会话与 CSRF 校验后才允许进入领域路由；路由方法入口用 `u.require(...)` 做第一次断言（`OrganizeRoutes.save/remove/assign/impact/members` 要求 `ORG_ADMIN`）；领域服务再做一次（`OrganizationService.list/save/deleteOps` 同样要求 `ORG_ADMIN`），避免将来有调用方绕过路由直接调用服务。删除类操作还会校验 `force` 语义，前端只负责提示，不构成授权。

会话与权限变更的既有约束对本次新增功能同样有效：人员权限被修改时会删除该账号的全部会话记录，因此撤销 `ORG_ADMIN` 或 `SELECTION_ADMIN` 后旧会话立即失效，下一次请求必须重新登录。

|权限|覆盖路径|拒绝语义|
|---|---|---|
|`ORG_ADMIN`|`GET /organizations`、`/organizations/impact`、`/organizations/members`、`/organizations/students`、`POST /organizations/save`、`/organizations/delete`、`/organizations/assign`|无权限 403「没有此操作权限」|
|（已登录即可）|`GET /organizations/options`|未登录 401；下拉数据只含编号与名称，不含人员信息|
|`GRADE_ADMIN`|`POST /enrollments`、`POST /enrollments/batch`|无权限 403；学生账号调用批量选课 403（已由端到端脚本覆盖）|
|`SELECTION_ADMIN`|`GET /selections`、`GET /selections/records`、`POST /selections/save`、`/selections/close`、`/selections/cancel`、`/selections/settle`、`/selections/batch`|无权限 403|
|`SELECTION_ENROLL`|`GET /selections/available`、`GET /selections/my`、`POST /selections/select`、`/selections/drop`|无权限 403；学生只能读写本人选课关系|

## 组织与选课的审计动作

敏感操作全部经 `RemoteRepository.mutate` 组装成一次 `Protocol.Mutation`，因此与既有成绩流程一样进入「数据库发件箱 + 独立加密账本」。

|审计动作|触发点|资源|快照内容|
|---|---|---|---|
|`ORG_SAVE`|`OrganizeRoutes.save` 新增或修改学院/专业/班级|组织编号|`colleges`/`majors`/`classes` 行的前后快照|
|`ORG_DELETE`|`OrganizeRoutes.remove`（含 `force` 级联）|组织编号|被删除行的 `before` 快照|
|`ORG_ASSIGN`|`OrganizeRoutes.assign` 批量调整学生/教师归属|目标组织编号|每个 `users` 行的归属字段前后快照|
|`SELECTION_PUBLISH`|`SelectionRoutes` 发布或修改选课批次|批次编号|`course_selections` 行的前后快照|
|`SELECTION_CLOSE`|关闭批次|批次编号|状态变更快照|
|`SELECTION_CANCEL`|取消批次并退回已选学生|批次编号|批次状态与退回结果|
|`SELECTION_SETTLE`|`POST /selections/settle`，或 `SelectionService.autoSettleExpired` 定时任务|批次编号|批次状态、被取消课程与自动退回人数；定时任务的操作人记为 `SYSTEM`|
|`SELECTION_SELECT`|学生选课|课程编号|`enrollments` 行与 `enrollment_records` 流水|
|`SELECTION_DROP`|学生退课|课程编号|同上|
|`SELECTION_BATCH`|教务按批次批量选课/批量退课|课程编号|每个受影响学生的关系行与流水|
|`ENROLLMENT_BATCH`|`POST /enrollments/batch` 按课程批量选课/退课|课程编号|每个受影响学生的 `enrollments` 关系行与 `ADMIN_ASSIGN`/`ADMIN_REMOVE` 流水|
|`ENROLLMENT_UPDATE`|`POST /enrollments` 单学生代选/代退|课程编号|该学生的 `enrollments` 行与对应的 `ADMIN_ASSIGN`/`ADMIN_REMOVE` 流水|

`ORG_ASSIGN`、`SELECTION_BATCH` 与 `ENROLLMENT_BATCH` 是批量动作：它们把同一次请求内的全部 `users`/`enrollments` 更新**连同各自的 `enrollment_records` 流水**放进同一个事务，因此要么整体成功并留下完整快照，要么整体回滚，不会出现「改了一半学生」的中间证据。审计写入失败时事务按既有失败关闭策略处理：拒绝敏感写入并要求先同步待发送事件。

## 组织与选课的鲁棒性校验

### 组织层级与编号

|校验|触发条件|响应|
|---|---|---|
|层级缺失或非法|`level` 为空或不属于 `COLLEGE`/`MAJOR`/`CLASS`|400「缺少组织层级 level」/「组织层级无效」|
|名称无效|`name` 缺失、空白或超过 100 字|400「字段无效：name」|
|同级重名|同表已存在同名记录且不是自身|400「同名学院/专业/班级已存在：…」|
|缺上级|新建专业未给学院、新建班级未给专业|400「必须指定所属学院/专业」|
|上级不存在|上级字段既不是合法编号也不是已存在名称|400「指定的学院/专业不存在：…」|
|班级与学院不一致|新建/修改班级时同时给出学院与专业，但专业不属于该学院|400「所选专业「软件工程」不属于该学院，请检查学院与专业的对应关系」|
|编号用尽|学院号段已达 99，或专业/班级在本号段内的本级序号已达 999|409「学院/专业/班级编号已用尽」|
|上级号段缺失|上级编号不满足「字母 + 5 位数字」，无法推导号段|400「缺少所属学院/专业，无法生成编号」|
|学制越界|`years` 不在 1–10|400「学制年限无效」|

编号格式由 `Models.validCode`/`codePattern` 统一约束为「单字母前缀 + 5 位数字」，`Models.levelOfCode` 可按前缀反查层级；因此编号自带层级信息，前端传入错层编号时不会静默通过。`OrganizationService.sequenceOf` 取第 2–3 位作为号段、`itemOf` 取末 3 位作为本级序号，两者都不满足格式时分别返回 `null` 与 `0`，不会因脏数据抛异常。

#### 编号不可篡改：只有一个主键 id（第三轮）

组织编号就是主键 `id`，它是**服务端拥有的字段**，客户端无法通过接口改写或伪造：

|攻击面|防护|
|---|---|
|编辑表单里改号|前端组织管理表单已经不提供「编号」输入框（第三轮删除），列表只把主键 `id` 作为只读文本展示；即使请求体里塞入 `id`/`code`，`OrganizeRoutes.save` 的修改分支也只用 `id` 定位对象，写库时不改主键|
|新增时自报编号|新增分支（不带 `id`）一律由 `OrganizationService.save` → `nextId` 生成主键，请求体里的 `code` 被忽略、也不会写库|
|把名称当编号引用|`resolveOwn` 只按 `id` 与 `name` 解析组织；编号是唯一的主键，不存在第二套编号可被冒充|
|编号耗尽后的越权分配|号段上限 99、本级序号上限 999，超出直接 409，不做回绕；序号取「现存最大值 + 1」，因此删除序号最大的对象后该编号会被再次分配——编号可用但**不保证永不复用**，历史引用以审计快照为准|
|遗留 `code` 列被误用|`colleges`/`majors`/`classes` 表仍保留第二轮的 `code` 物理列（避免再触发整库重建），但组织接口不读写它：`/organizations` 与 `/organizations/options` 用 `copy.remove("code")` 保证响应里没有该键，`OrganizationService` 也不再提供 `nextCode`/`maxCode`/`codeOf`|

### 组织归属中的管理员约束（第二轮）

管理员是全局角色，不归属任何学院、专业或班级，因此它的三级组织字段必须是空值。这条约束在三处落实，覆盖「保存账号」「调整归属」「读取自身信息」三条路径：

|位置|行为|
|---|---|
|`AdminService.saveUser`（`POST /users/save`）|`role=ADMIN` 且请求体带了任何一级组织 → 400「管理员不归属学院、专业或班级」；校验通过后三级字段一律写空串（库中以空串表示「不设置」）|
|`OrganizeRoutes.requireRole`（`POST /organizations/assign`）|把管理员列进 `studentIds`/`teacherIds` 或通过班级整体迁移命中管理员时 → 400「管理员不归属学院/专业/班级」，不写入任何归属字段|
|`CoreRoutes.me`（`GET /me`）|管理员的三级组织编号为空，`collegeName`/`majorName`/`className` 返回 `null`；前端身份行据此只显示角色，不显示「管理员 · null」|
|`DemoInitializer.verifyOrganizationIntegrity`（启动自检）|初始化结束时逐行校验账号的三级归属：管理员带组织直接抛异常中止启动；非管理员的学院必须是合法学院编号（专门拦截「学院被写成专业编号」）、专业必须属于该学院、班级必须属于该专业|

允许管理员的三级字段全空，也意味着按组织筛选的列表（组织成员、学生名册）天然不会返回管理员——这是需求要的结果，而不是统计遗漏。

### 组织删除保护

|场景|结果|
|---|---|
|组织下仍有课程|409「该学院/专业/班级下仍有课程，不能删除」|
|学院/专业下仍有下级且未 `force`|409「该…下仍有 N 个下级，需确认级联删除」|
|下级组织中仍有课程|409「下级专业/班级仍有课程，不能删除」|
|组织仍被账号引用|409「该…下仍有账号，请先调整人员的组织归属」|
|`force=true` 且下级无课程、无账号|级联删除下级后删除本级，全过程一次事务 + 一条 `ORG_DELETE` 审计|

注意 `force` 只跳过「有下级」这一条确认，**不跳过**课程与账号引用检查——这是刻意的：级联删除可以删结构，但不能删掉仍被成绩、选课或审计引用的归属。

### 批量调整人员归属

|校验|响应|
|---|---|
|未提供 `studentIds`、`teacherIds` 或 `classId`|400「请指定要调整的学生或教师」|
|把学生调整到非班级层级|400「学生只能调整到班级」|
|把教师调整到非专业层级|400「教师只能调整到专业」|
|目标账号角色不符|400「只能调整学生/教师账号」|
|目标账号不存在|404「记录不存在」|
|单次超过 `Models.MAX_BATCH_STUDENTS`（300）人|400「单次调整的账号数量过多」|

|课程学期与批次学期不一致|400「课程学期与选课学期不一致：课程名」|
|课程已停开（`status=CANCELLED`）|409「已停开课程不能发布选课」|
|**课程已有教师录入成绩**（`grades` 存在任意状态的行）|409「该课程已有教师录入成绩，不能发布选课」|
|课程已存在于其他 `OPEN` 批次|409「该课程已存在于其他进行中的选课发布」|
|范围里的组织不存在|400「指定的学院/专业/班级不存在：…」|
|对 `CLOSED`/`CANCELLED` 批次执行关闭或结算|409「选课未开放」|
|重复取消同一批次|409「选课已取消」|

这些校验全部在写入前完成，任何一条失败都不会产生半条记录；`course_ids` 的去重也是先算后写。

### 学生选课与退课校验

选课按固定顺序短路校验：批次存在 → `OPEN` → 时间窗口 → `allow_add` → 角色为 `STUDENT` → 账号启用 → 选课范围 → 课程属于本批次 → 课程存在且未停开 → 学期一致 → 未重复选课 → 同课程代码冲突 → 此前未通过 → 挂科重修许可 → 学分上限。失败响应见 [API 文档](api.md) 的 3.8 节。

|风险点|防护|
|---|---|
|越权代选他人课程|`select` 只以会话用户身份写入，请求体里的 `studentId` 不被采纳|
|越权代退他人课程|`drop` 只有在用户持 `SELECTION_ADMIN` 时才接受 `studentId`；否则 403「只能退选本人的课程」|
|窗口外选课|`requireWindow` 比较 `Instant`，未开始 400、已结束 400；`/selections/available` 直接把窗口外批次从列表剔除，避免出现「看得到选不上」|
|抢课与重复提交|`enrollments(course_id,student_id)` 唯一索引 + 服务端「已选」判断（409）；重复提交同一请求只会得到 409，不会产生第二行|
|退课抹掉成绩证据|存在任意状态成绩行即 409「教师已录入成绩，不能退课」；退课只改 `status`，不删除行|
|绕过范围限制|范围判定在 `checkSelectable` 内，与 `/selections/available` 的 `eligible` 共用同一函数，前端改参数无效|
|批量操作放大影响|单次最多 300 人；逐人校验并记录 `failed`，成功项在同一事务提交，失败项不影响他人|
|时间字段被伪造|时间只用于比较，落库统一为本地 ISO-8601；服务端不接受客户端指定的状态或操作人|

### 重修判定与三条同课程代码规则（第四轮）

重修在数据上**不是**课程属性，也没有单独的「重修报名」入口：它是「同一课程代码在后续学年重新开设」时，由历史成绩推导出的学生状态。判定与拒绝全部集中在 `SelectionService.codeHistory`/`checkSelectable`（`CourseService.failedCodesBefore` 给教师名单用同一口径）：

|规则|判定条件|响应|
|---|---|---|
|重修状态（不拒绝，只标记）|该生在**更早学期**、**同一 `code`** 上存在成绩 `state=SUBMITTED` 且**有效分 < 60** 的修读记录 → 本学期这条记录 `retake=true`、`retakeLabel="重修"`|接口下发标记；前端用徽标显示，课程名不变|
|已通过不得重选|更早学期同一 `code` 存在 `SUBMITTED` 且有效分 ≥ 60 的记录|409「该课程此前已通过，不能重复修读」（`PASSED_BEFORE`）|
|同代码同学期冲突|本学期已经选了同一 `code` 的**另一个教学班**|409「本学期已选择同一课程代码的其他教学班」（`CODE_TAKEN`）；唯一例外是该生此前挂科且本次批次 `allow_retake=1`|
|未开放重修|该生此前挂科（重修场景），但批次 `allow_retake=0`|403「本次选课不允许重修」（`RETRY_FORBIDDEN`）|

口径细节与防护：

- **只有「已提交的挂科」才算重修依据**：`state=SUBMITTED` 且按课程权重算出的有效分 < 60（`Models.effective`，补考按 60 分封顶后取较高者）。成绩未出、仍是草稿（`DRAFT`）、或已退课（`status=DROPPED`）的记录都不参与判定，避免把「正在修读的第一次」误判成重修。
- **判定与教学班无关、只与 `code` 和学期先后有关**：同一课程号连续多个学期重修仍显示为「重修」；更晚学期的记录不构成「此前修读」。
- **批量场景一次性读入成绩索引**：`failedCodes` 先建 `course_id|student_id → grade` 索引再逐条比对，避免为了标记重修而对每门课单独查成绩（否则 `/selections/available` 会退化成 N 次远程查询）。
- **不把重修写进课程名**：课程名加了「重修」后缀会造成「两门不同课程」的假象，也会与「同一课程号」的判定自相矛盾；因此课程名一律保持原样，谁在重修由 `retake`/`retakeLabel`/`retakeCount` 下发，并且演示数据在启动时由 `DemoInitializer.verifyTranscriptIntegrity()` 校验「同一课程号最多两次修读、前一次必须是已提交的挂科、后一次已提交则必须通过、至少 3 名重修学生」，不满足直接中止启动。
- **数据未出成绩时的展示**：当前学期（2026-1）正在重修的学生成绩尚未提交，因此他们的记录同样满足 `retake=true`（依据是更早学期的挂科），教师在名单里看到「重修」徽标并现场录入成绩；录入并通过后，该生此课程号即进入「已通过」状态，后续再选会被 `PASSED_BEFORE` 拒绝。
- **判定链路上不能有静默失败**：重修判定把「成绩算不出来」当作「不是重修」，因此任何异常都可能让挂科学生悄悄失去重修标记。第四轮修复的 `Models.total` 就是这类问题——系数表缺项时它曾抛 NPE，被两个判定入口的 `catch (RuntimeException ignored)` 吞掉；现在缺失系数按 0 权重处理，缺项只让该分项不参与计算，不会把整门课判成「无成绩」（`ModelsTest` 覆盖该分支，详见 [decisions.md](decisions.md)）。

### 暂存（DRAFT）成绩的边界（第五轮）

暂存成绩是**教师的在途录入**，不是学业结论。它在系统里的可见范围被刻意收窄，这样「补一条暂存成绩让预测有对象」不会污染任何既有判定：

|是否参与|说明|
|---|---|
|**不**算通过、**不**算挂科|通过/挂科只由 `state=SUBMITTED` 的有效分决定（`>= 60` 通过）|
|**不**进入学业记录|`GET /transcript` 只查 `state=SUBMITTED`（`repo.find("grades", Map.of("course_id", …, "state", "SUBMITTED"))`），学生看不到暂存行|
|**不**参与重修判定|选课侧 `SelectionService.failedCodes`/`codeHistory` 与教师名单侧 `CourseService.failedCodesBefore` 都要求成绩已提交且有效分 < 60；`markRetakes` 也只比较学业记录里的学期，暂存行不在其中|
|**不**影响学分与未通过统计|「我的成绩」的已获课程/已获学分/未通过课程三个统计都基于 `/transcript` 的已提交记录|
|**会**出现在|教师端成绩表（可继续编辑、提交、撤回）；`POST /predict` 的预测对象（正是「已有平时与实验、期末未录入」的学生）|

因此演示数据给可预测的学生写入的暂存成绩（只有平时与实验分）只承担两个作用：让教师有可现场录入的成绩行、让学业预警有可预测的对象。`DemoInitializer.verifyPredictionCoverage()` 在启动时对**每一门有 ACTIVE 选课的课程**校验「≥3 个更早年份 + ≥24 条三分项齐全的已提交成绩 + 本班至少 1 人缺期末」，不满足直接中止启动，避免用户点开页面才发现功能不可用。

另一层边界在**历史样本教学班**：学业预警的训练样本需要更早年份的成绩，这些教学班**只写成绩、不写选课记录**（任课教师是 `seed-history` 这个非真实账号）。这样它们不会出现在任何教师/学生的课程列表、名单或「我的课程」里，也不会被当成「有学生选课的正课」——否则它们自己又会成为需要 3 个更早年样本的课程，形成无限回归。**样本成绩只用于训练**，不构成任何人的学业记录：判定重修、算学分、出成绩单都只读真实选课关系对应的成绩行。同理，对学生**已经出分的历史课程**调用 `/predict` 会得到 200 + 空 `results`（没有「期末未录入」的对象），这不是数据不足（那是 422），前端会引导改选当前学期的课程。

### 按课程批量选课校验（第二轮）

`POST /enrollments/batch` 是教务在课程界面直接维护名单的入口，权限为 `GRADE_ADMIN`（`SelectionService.batchByCourse` 入口即 `u.require("GRADE_ADMIN")`）。它的目标学生是「显式名单 ∪ 班级全体」的并集，因此校验分两层：先守住请求本身的边界，再逐人判定。

|校验|触发条件|响应 / 行为|
|---|---|---|
|课程不存在|`courseId` 在课程索引里找不到|404「课程不存在」|
|目标为空|`studentIds` 与班级都没给|400「必须指定学生名单或班级」|
|班级不存在|`classId`/`className` 经 `resolveOwn` 解析不到|400「指定的班级不存在」|
|并集为空|给定对象里没有任何 `role=STUDENT` 的账号|400「没有找到可操作的学生」|
|超出批量上限|去重后的目标学生数 > `Models.MAX_BATCH_STUDENTS`（300）|400「单次批量操作最多 300 名学生」|
|账号不存在|目标账号查不到|该学生进 `failed`，原因「学生不存在」|
|非学生账号|目标账号 `role != STUDENT`|该学生进 `failed`，原因「仅学生可选课」；管理员因此永远无法被批量选课写入|
|账号停用|选课时 `enabled != 1`|该学生进 `failed`，原因「账号已停用，不能选课」|
|重复选课|该生该课程已有 `status=ACTIVE`|计入 `skipped`，不报错、不产生第二行|
|已有成绩退课|退课时存在任意状态的 `grades` 行|该学生进 `failed`，原因「教师已录入成绩，不能退课」，其余学生照常处理|
|重复退课|退课时没有 `ACTIVE` 记录|计入 `skipped`|
|唯一索引冲突|曾经退课的 `DROPPED` 行被再次选入|复用该行走 `UPDATE`（不会 `INSERT` 第二行）|

设计要点：**逐人失败不中断整批**。与单学生接口不同，批量接口把「个别学生不满足规则」表达为返回值里的 `failed[]`（含学生姓名与原因），只把请求级错误抛出为 4xx；所有成功项的关系行与流水在同一个 `repo.mutate`（审计 action `ENROLLMENT_BATCH`）里提交，因此不存在「处理了一半但没有审计」的状态。选课与退课分别写 `ADMIN_ASSIGN`/`ADMIN_REMOVE` 流水，原因是「教务按课程批量选课」/「教务按课程批量退课」，操作人是当前管理员的会话身份（请求体无法指定 `operator`）。

该接口**刻意不检查**批次时间窗口与 `allow_add`/`allow_drop`：教务处理学生申请时窗口往往已关闭，代选的业务语义就是窗口外的授权操作。代价是它对批次开关不敏感，因此这条路径的能力边界完全由 `GRADE_ADMIN` 权限与审计账本承担，而不是由批次配置承担；批次维度的 `POST /selections/batch` 仍保留完整规则校验，两者在审计里可按 action 区分。


### 结算与自动退回

|校验|响应 / 行为|
|---|---|
|对非 `OPEN` 批次结算|409「选课未开放」|
|人数 ≥ `min_enroll` 的课程|不退回，保持原样|
|人数 < `min_enroll` 的课程|选课记录置 `DROPPED`、写 `AUTO_REFUND` 流水、课程 `status=CANCELLED`、批次最终置 `CLOSED`|
|定时任务 `autoSettleExpired`|每 60 秒扫描一次，只处理 `end_time` 已过的 `OPEN` 批次；单批次异常只打印日志，不中断调度线程|
|审计归属|手工结算操作人是管理员账号，定时结算操作人是 `SYSTEM`，两者都可从账本与流水区分|

自动退回只改状态、不删除 `enrollments` 行，因此「曾经选上、后来被退回」这一事实仍可核对；退回原因里带课程名称与 `min_enroll` 数值，管理员不需要反查配置。

### 已知边界

- 选课没有名额上限（`course_selections` 没有容量字段），因此不存在「抢课超卖」的问题，但也不支持限选人数与候补队列。
- 并发选课依赖 `enrollments(course_id,student_id)` 唯一索引兜底：同一学生并发提交两次，可能一次成功一次因唯一索引冲突失败并返回 5xx/409，而不是业务文案。
- 组织维护未按学院划分数据域：持有 `ORG_ADMIN` 的管理员可以维护任意学院的组织与人员归属。
- `selectedCount` 统计含 `DROPPED` 的历史人次，与课程级 `enrolled`（仅 `ACTIVE`）含义不同，报表不能混用。
- 组织编号只有一个主键 `id`，其唯一性由数据库主键约束保证；`colleges`/`majors`/`classes` 表里遗留的 `code` 列不再有业务含义，也没有唯一索引——它只是第二轮「显示编号」未清理的物理列，接口不读写、响应不下发。
- 按课程批量选课不做批次开关与时间窗口校验，能力边界完全由 `GRADE_ADMIN` 权限承担；这是刻意的语义，不是遗漏，见上文「按课程批量选课校验」。

## 网络部署

默认所有服务监听 127.0.0.1，仅浏览器访问 8443。本地各进程也使用 TLS，并实际验证服务器证书。正式网络只公开网关 443；9441 仅允许网关子网；9442 仅允许业务服务；9443 仅允许业务/数据服务；链工具禁止公网入口。宿主机防火墙、VPN、IDS 为部署职责，工程未宣称已在用户机器安装防火墙或入侵检测设备。

网关只支持 GET/POST，业务数据与内部路径分离。对于内部已认证服务的进一步隔离，可升级到双向 TLS 和请求摘要中的用户身份断言。当前 TLS 为服务器认证加应用层 HMAC，未实现 mTLS。

## 区块链与模型适用范围

Ganache 是单机以太坊测试链，不是多组织共识网络。程序真实提交 EVM 交易并验证 receipt，不能把单机链描述成不可被本机管理员重写的公有链。当前交易锚定不依赖智能合约，使用标准交易 input 写入摘要。

链服务未公开 JSON-RPC/WS，只通过 HMAC 保护的三个本机 HTTPS 方法访问嵌入式 provider。测试账户固定且自动补充测试 gas，禁止接入真实资产。安全审计发现 Ganache 捆绑依赖仍有已知漏洞，不能通过普通 npm overrides 完整修复，详见测试报告。正式方案应迁移到维护中的外部 EVM 节点或 Fabric，密钥由托管签名服务持有。

线性回归、决策树与 LSTM 实际训练和运行，但演示数据不支持现实准确率声明。LSTM 的合成验证准确率不能直接用于衡量校园违规识别质量；必须由管理员人工复核。无自动处分、无自动修改成绩行为。

## 应急操作

1. 出现完整性错误：暂停相关业务录入，保留日志、账本、链数据与数据库只读快照，记录系统时间和文件 SHA-256。
2. 管理员在独立审计页核查原始成绩；不要重置密钥、删除坏账本行或清空 outbox。
3. 判断是密文损坏、版本回退、数据库删除、链不可达、证书过期还是文件写失败。密码/角色事件与操作者记录可定位影响范围。
4. 隔离受影响进程和服务账号，撤销会话，轮换泄露密钥前准备旧数据迁移。
5. 从已验证的离线备份恢复，在隔离环境运行完整性校验；保留修复前证据，再通过授权成绩维护流程修正。
6. 恢复后运行 API、安全和业务回归，核对 outbox=0、账本 verified=true，记录复盘和负责人。

如果链锚定成功但账本追加失败，当前服务会因链/账本长度差异停止写入。应从事务发件箱/审计服务文件备份恢复对应密文块，校验既有链交易；不得简单删除链上锚定。此人工恢复窗口是当前教学实现的已知局限，后续应持久化审计追加意图并实现 crash recovery。
