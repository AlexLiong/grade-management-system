## 决策及理由

### 远程方法选择 HTTPS Webservice

PDF 接受 RMI、CORBA、Webservice 等。选择 HTTPS JSON 便于跨操作系统和前端统一，仍通过 Serializable 风格值对象实现远程参数传递和两个精确 Java 接口。HTTP 状态承载失败语义，成功二维字符串数组/布尔返回满足规定。

### 参数化 SQL 替代值拼接

服务器自动生成 SQL 结构，字段类型由白名单定义并转换。使用参数绑定自动处理数值和字符串，满足类型适配同时避免 SQL 注入；不照搬直接给字符串加引号的示例实现。

### 优先轻量注册发现

四个服务规模无需默认引入完整 Spring Cloud 运维体系。自带租约、实例身份、白名单注册与轮询，展示跨进程解耦和业务副本扩容；明确注册中心/审计单点和迁移路径。

### 独立网络证据

数据库内日志与业务成绩同库，不能单独满足“不依赖数据库查原始成绩”。采用独立进程文件账本，保留完整前后快照，额外进行 EVM 哈希锚定。明文不上链，保证学生成绩机密性。

### 完整性异常失败关闭

检测到密文、账本、链或待同步审计异常时不继续敏感写入。保留发件箱重试与原始证据，避免“只记录控制台警告仍允许连续改分”。分布式提交窗口仍需恢复方案，不虚构跨系统原子性。

### 可解释 AI

使用 Weka `LinearRegression` 和 `REPTree`，不自行发明回归/树算法。统计异常与模型预测分开，低于 55 分为强预警；55–60 为临界风险。模型显示历史年份、样本量、留后验证误差和树结构；不能把演示集结果当成真实校园精度。

### OCR 在浏览器执行

选用 Tesseract.js 本地模型，避免云 OCR 凭据、网络上传学生成绩单和临时文件残留。只识别学号/数字列，用户确认后转普通草稿，不自动提交。

### 组织编号作主键，前端按名称操作

学院/专业/班级以 `C01001`/`M01001`/`B01001` 这样带层前缀的可读编号作主键，而不是随机 UUID：编号本身编码了层级与号段，审计快照、成绩单和排错时无需再联表即可读懂。编号固定 6 位 = 1 位层前缀 + 2 位号段 + 3 位本级序号：学院的号段是它自己的递增序号（取现有学院第 2–3 位最大值 +1，本级序号从 `001` 起），专业与班级沿用上级的号段，本级序号在号段内递增。这样新建学院既不会与已有学院撞号，也不会占用已经被某个学院的下级使用的号段。代价是编号生成要读全表取最大值（`OrganizationService.nextId` 配合 `sequenceOf`/`itemOf` 扫描），演示规模下可接受，生产应改为序列表或数据库序列；另外学院号段上限只有 99、专业/班级本级上限 999，超出直接 409 而不是进位。

与之配套的是「前端按名称操作」：请求体里的组织字段既接受编号也接受名称，由 `resolveOwn` 先按 `id` 再按 `name` 解析；响应通过 `names`/`enrichOwn`/`nameField` 附加 `collegeName`、`majorName`、`className`。这样浏览器不需要维护一张编号表，也不会出现「前端自己拼名称」这第二种真相。已知取舍：`resolveOwn` 按名称查询，同名组织在同一层被 `save` 拒绝（同名判定在 `OrganizationService.save`），所以名称在同一层内保持唯一。

### 组织删除采用保护而非默认级联

删除组织时先查课程与账号引用：仍有课程直接 409；仍有下级要求 `force=true` 才级联；下级仍有课程或账号时递归失败。禁用（`enabled=0`）用来表达「不再招生」，删除只用于真正录错的记录。理由与人员维护一致：成绩、选课和审计事件都按组织编号引用，物理删除会让历史证据产生悬挂引用。前端把 `impact` 的影响面先展示给管理员，再决定是否按 `force` 重试一次。

### 选课证据分成「当前关系」与「动作流水」两层

`enrollments(course_id, student_id)` 有组合唯一索引，表达学生的当前选课关系，新增 `source`/`publish_id`/`selected_at`/`status` 记录来源、批次、时间与是否已退课；`enrollment_records` 是只增不改的动作流水，记录 `SELECT`/`DROP`/`ADMIN_ASSIGN`/`ADMIN_REMOVE`/`AUTO_REFUND` 及原因与操作人。

不用「只留流水」是因为每次查名单都要回放全部历史；不用「只留关系」是因为自动退回、教务代选这类动作需要留下原因，而独立账本的定位是安全证据而不是业务报表。两层合起来＝可查询的当前状态 + 可解释的变更历史。代价是同一事实存在两份投影，因此两者始终在同一个 `Protocol.Mutation` 事务里写入。

### 最低开课人数不足由结算触发退回

`min_enroll` 不做「达到人数就自动开课」的正向判定，而是在结算时反向判定：对该批次每门课程统计 `ACTIVE` 选课人数，不足的课程判定为不开课——逐条把选课记录置为 `DROPPED`、写 `AUTO_REFUND` 流水（原因里带课程名与人数门槛）、把课程 `status` 置为 `CANCELLED`，最后把批次置为 `CLOSED`。

结算有两个入口，但**共用同一个 `SelectionService.settleBatch`**：教务点「结算」走 `POST /selections/settle`（操作人记管理员账号），窗口结束后则由 `@Scheduled(initialDelay = 15000, fixedDelay = 60000)` 的 `SelectionService.autoSettleExpired` 每分钟扫描 `end_time` 已过的 `OPEN` 批次自动执行（操作人记 `SYSTEM`）。定时任务在业务启动类已开启的 `@EnableScheduling` 下生效，整体 try/catch，单个批次失败只打印日志、不中断调度。

这样选课期间的学生端结果稳定——不会因为中途有人退课导致某门课「瞬间不可选」；退回是一次可审计的批量动作，而不是分散在每次选/退课里的隐式副作用。代价有两点：结算只在 `OPEN` 状态允许，已关闭的批次不会再被重新结算；定时任务依赖业务进程存活，进程停机期间不会补算，需要管理员手工结算。另外「同一份逻辑两个入口」意味着不能用「谁调用的」来区分语义，因此审计里必须看 `operator` 才能判断是人工还是自动。

### 选课窗口、退课与批量代选的取舍

- 退课只改 `enrollments.status`，不删除行：既有成绩、流水与审计都引用这行，删除会造成悬挂引用；同时 `(course_id,student_id)` 唯一索引要求重新选课时复用同一行（`UPDATE` 回 `ACTIVE`）。
- `select` 与 `drop` 对时间窗口的要求不同：选课必须 `OPEN` 且在窗口内，退课允许 `OPEN` 或 `CLOSED`（只拒绝 `CANCELLED`）。这是刻意的——关闭选课之后仍应允许学生调整，只有整批作废才冻结关系。
- 教务批量代选**跳过时间窗口**但保留其余规则：代选的业务场景就是处理学生的特殊申请，此时窗口往往已经关闭；但「已通过不得重选」「学分上限」这类学术规则不能因为代选而放宽。
- 规则集中在一个 `checkSelectable`：`/selections/available` 的 `eligible`/`reason` 与真正选课的报错来自同一段代码，避免出现「页面显示可选、点了却报错」的两套口径。代价是列表接口要为每门课跑一遍完整校验（含成绩查询），课程数多时会变慢。
- 「已有成绩不得发布选课」判定的是 `grades` 表存在任意状态的行（含 `DRAFT`），比「已提交」更严格：草稿一旦存在，说明教师已经开始录入，此时再开放选课会让成绩与名单同时变动。

### 同一学期允许多个教学班共用同一课程代码

`CourseService.saveCourse` 曾经强制 `(code, term)` 唯一，即同一学期只能开一个使用某课程代码的教学班。本次移除了这条校验。

原因是它与选课需求直接冲突：教务需要让「同一门必修课由不同教师分别开课，学生选择其中一位」，而这必然产生同一学期、同一课程代码的多个教学班。唯一性约束放在开课环节，等于禁止了这种排课方式。现在改为在**选课环节**保证不重复修读：`SelectionService.codeHistory` 判定同一学生在同一学期是否已经选了同一课程代码的其他教学班（409「本学期已选择同一课程代码的其他教学班」），以及此前学期是否已经通过该课程代码（409「该课程此前已通过，不能重复修读」）。

这个改动的代价是数据库不再有 `(code, term)` 这一层兜底，重复修读只能靠业务规则拦截——如果将来出现绕过选课接口的直接写库，约束不再生效。因此 `enrollments(course_id,student_id)` 的组合唯一索引仍然保留，它拦的是「同一学生重复选同一教学班」这一更基本的情形。该改动直接来自一次失败的功能测试：端到端脚本第一次运行 108/112，4 条失败全部落在这个场景。

### 重修不体现在课程名

用户明确要求：重修不能体现在课程名上。第一轮的演示数据里曾有一门课直接在课程名后追加了表示重修的括号后缀，这会造成两个假象：一是看起来像两门不同的课程，二是与「同一课程号才是同一门课」的判定口径自相矛盾——`SelectionService.codeHistory` 与教务排课都按 `code` 关联修读历史，而展示层却给出了两个课程名。

现在的做法：

- **重修 = 同一课程代码在后续学年重新开设的教学班**（同一 `code`、不同 `term`），课程名、学分与权重都可以与原教学班完全一致，`courses` 表上**没有任何重修字段**；
- 「谁在重修」完全由**历史成绩**推导：更早学期 + 同一 `code` + 成绩 `state=SUBMITTED` + 有效分 < 60。`SelectionService.FailedCodes`（学生端「我的选课」「选课台」与教务端批次课程）与 `CourseService.failedCodesBefore`（教师端名单）共用这一口径，成绩未出/未提交与已退课都不算；
- 状态以**字段**下发而不是改名：学生 `/selections/my`、`/selections/available` 与教师 `/roster` 得到 `retake`/`retakeLabel`，教务 `/selections` 得到课程级 `retakeCount`；前端用「重修」徽标展示，课程名保持原样。

代价与配套有三点：

1. 判定是**派生**结果而不是持久化状态，因此每次查询都要读历史成绩。批量场景（选课台、教师名单、批次课程列表）必须先一次性读入 `course_id|student_id` 成绩索引再比对，否则会退化成 N 次远程查询——这也是 `effectiveScore` 增加「可复用成绩索引」重载的原因。
2. 「重修」没有独立的业务表与流程（没有报名、没有审批、没有次数限制）。它只表达「这名学生此前挂过同一课程号的课」；若将来需要重修报名或收费等流程，应新增业务表，而不是往课程名或课程行上挂标记。
3. 派生口径必须靠数据自检保护：`DemoInitializer` 在灌数后执行 `verifyTranscriptIntegrity()`——同一课程号最多两次修读（挂科与重修各一次）、前一次必须是已提交的挂科（有效分 < 60）、后一次若已提交必须通过（有效分 ≥ 60）、至少 3 名重修学生且轨迹必须与 `RETAKES` 清单一致，不满足直接抛异常中止启动。

演示数据据此给出 5 名重修学生、覆盖 3 个课程代码：3 人在 2024-1 重修通过（`CS102`/`MG101`/`CE101`），2 人在 2026-1 当前学期重修（`CS102`，只接收重修学生的教学班 `c35-cs102c`，成绩未提交，教师登录即可现场录入）。

### 学业记录的重修判定只看「更早学期是否存在同一课程代码」

学生端「我的成绩」原来只有 `failed`（是否挂科），看不到「这门课是不是重修」，而重修在数据上又不体现在课程名里，于是学生无法从成绩单判断自己哪次是重修。第五轮给 `GET /transcript` 的每条记录加了 `retake`/`retakeLabel`。

判定实现刻意做得比选课侧更简单：**同一 `code` 在更早学期还有一条记录，本学期这条就是重修**（`GradeService.markRetakes`）。之所以不需要再判断「上一次是否挂科」，是因为两个前置约束已经把它排除掉了：

1. `/transcript` 只包含 `state=SUBMITTED` 的成绩——正在修读（成绩未提交/暂存）与已退课都不在记录里，所以「出现两次」必然对应两次已出结果的实际修读；
2. 选课规则禁止已通过的课程再次修读（409 `PASSED_BEFORE`），演示数据的 `verifyTranscriptIntegrity()` 也保证「跨学期同代码的前一次必是挂科」。因此同一代码出现第二次，唯一可能就是第一次没通过。

代价与边界：这条判定依赖「数据里不存在已通过又重修的脏数据」。一旦有人绕过业务规则直接写库造出「通过后重修」，学业记录会把它标成重修而不报错——所以它靠启动自检兜底，而不是靠每次查询重新推导。另外，`markRetakes` 里的比较是**学期字符串**（`2024-1 < 2025-1`，`2024-1 < 2024-2`），不做日历运算，这与全项目其它地方（`codeHistory`、`batchPublish`）保持一致。前端据此在课程名后加「重修」徽标，课程名本身仍然不变。

### 学业记录的统计口径按课程代码去重

「我的成绩」页面的三个统计（已获课程门数、已获学分、未通过课程数）在加重修标记时暴露了口径问题：直接按记录行累加会让重修学生看到自相矛盾的数字——同一门课修两次算两门课、学分重复累加、已经重修通过的课程仍留在「未通过」里。

第五轮把三者统一为**按课程代码去重**（`App.vue` 的三个 computed）：

|统计|口径|
|---|---|
|已获课程数 `passedCourseCount`|按 `code` 去重后 `failed=false` 的课程数（重修通过只算一门）|
|已获学分 `earnedCredits`|按 `code` 去重、只取通过的那一次记录的学分（重修不重复计学分）|
|未通过课程数 `pendingCourseCount`|**至今仍未通过**的课程代码数（先收集已通过的代码，再统计「挂科且不在已通过集合里」的代码）|

这样口径与毕业学分审查、成绩单展示的直觉一致：学分只认一次通过，未通过以「当前是否仍欠这门课」为准。代价是需要遍历一遍学业记录并在前端做集合去重（教学规模可接受）；如果将来把统计搬到服务端，应保持同一口径，避免出现「页面数字」与「导出成绩单」两套算法。

### 历史样本教学班同样有名单

学业预警要求「被预测课程在更早学期有 3 个不同年份、≥24 条三分项齐全的已提交成绩」。正课最早只到 2023-1，要凑够 3 个年份必须补历史教学班（`SAMPLE_LAYERS` → `SAMPLE_COURSES`，2020-1 / 2021-1 / 2022-1 / 2023-2 共 91 个，id 形如 `h-2020-1-cs101`）。

施工时曾担心**无限回归**：这些历史班一旦有学生选课，它们自己就变成「有学生选课、需要可预测」的课程，于是又得为它们再往前补 3 个年份。当时的规避办法是：样本班只登记成绩、不建选课记录。**这个顾虑现在被证明不成立**：2020-1 / 2021-1 / 2022-1 / 2023-2 本身就是数据里最早的期次，它们**没有更早学期可查**，因此永远不会成为「需要自己 3 个更早年样本」的课程；无限回归只在「补出来的历史班仍然晚于某个更早期次」时才会发生。校验逻辑也据此收敛：`verifyPredictionCoverage()` 只校验 **64 门正课**，并在遍历时显式排除 `SAMPLE_COURSE_IDS`——把样本班纳入校验会必然失败（它们不可能有更早年份），那是校验口径的问题而不是数据的问题。

因此现在每个历史样本教学班都有**完整的名单与成绩**：每班 8 条 `ACTIVE` 选课 + 8 条成绩（「有成绩的人恰好就是选了这门课的人」），91 个班共 728 条样本成绩。任课教师是 4 个真实的教师账号 `ht2020` / `ht2021` / `ht2022` / `ht2023`（姓名「史料教师·2020-1」等，`TEACHER` 角色，信息工程学院·软件工程），各自只带一个学期的历史班（18 / 30 / 30 / 13 门）；它们被写入 `DISABLED_USERNAMES`，**`enabled=0` 不可登录**——既让课程有真实归属，又不会让人误以为这是可用的演示账号（原先把任课教师写成非真实账号的做法已取消）。

配套的第二层是**缓考样本池**（`B01006`）：为每门已提交成绩的正课补 1 名「有平时与实验、缺期末」的学生（暂存 `DRAFT` 成绩）。只补历史样本还不够——如果当前课程里没有任何「期末未录入」的学生，`predict` 依然会返回空 `results`，用户看到的还是「没有预测结果」。两层合起来才能让**每一门有选课的正课**都真的能预测：`verifyPredictionCoverage()` 遍历所有有 ACTIVE 选课的**正课**，校验「≥3 个更早年份 + ≥24 条样本 + 本班至少 1 人缺期末」，不满足直接中止启动（当前 64 门全部通过）。

顺带纠正一处旧说法：历史样本学生**有自己的选课记录**，因此他们那 8 条成绩**确实会进入本人的学业记录**（「我的成绩」里能看到），这与真实学生的行为一致；他们与正课学生是不同账号，样本班又处在最早期次，所以不会产生任何「跨学期重复修读」或重修误判。

代价与边界写法必须诚实：**预测只对进行中的课程有意义**。学生对已经出分的历史课程调用 `/predict` 会得到 200 + 空 `results`——那门课没有「期末未考」的对象，不是数据不足（数据不足是 422）。前端据此给了两处引导文案（页面顶部说明 + 选中已出分课程时的空态提示），端到端脚本也改成**逐门课**调用 `/predict` 验证「有选课的课程都可预测」，而不是只抽查一门。

### 测试残留由初始化器在启动时兜底清理

端到端脚本会在 `2027-2` 这类一次性学期里新建教学班与选课批次，而系统**没有课程/批次的删除接口**（课程只能用「取消教学班」下架），于是每跑一次测试，课程下拉与批次列表里就会多一批残留。第六轮加了 `DemoInitializer.purgeTestArtifacts()`：在**每次启动、且早于本次灌数**执行，判据是「名称含『测试』或『低人数』」＋「学期/批次不在演示数据声明的学期集合内」；按 `course_id` 级联清理 `enrollments`/`grades`/`enrollment_records`/`analyses`/`courses`，并删除名称含「测试」的 `course_selections`（连同其流水）。日志打印清掉的门数/选课数/成绩数/批次数，没有残留时打印「未发现测试课程/测试选课批次残留」。

为什么放在初始化器而不是加一个删除接口：删除接口会把「误删演示数据」的风险暴露给任何调用方，也与「课程不做物理删除、只取消」的既有取舍冲突；初始化器本来就掌握「哪些学期是合法的」这份真相，用它做判据最不容易误伤。代价是残留只在**下次启动**时清掉——跑完测试不重启仍会看到测试课程，需要在收尾时重启一次服务（不再必须 `-ResetDb`）。

### 账本尾部截断不会破坏哈希链：用锚点数补检测

独立账本的 `verifyLocal()` 只校验「区块之间的链接 + HMAC」，因此**从尾部截断区块不会破坏任何哈希链接**——删掉最后 N 块后剩下的链依然自洽，`/audit` 会静默少返回 N 条记录，而本地校验仍然通过。这是本轮在性能优化过程中由测试发现的一个真实缺口（原先只考虑到「中间篡改」与「整文件替换」）。

修法是 `requireNotTruncated()`：读 `anchors.json` 里已锚定的区块数，要求**本地账本不得比链上锚点更短**（只查「更短」——账本比锚点多属正常中间态：新区块先落本地账本、再逐块锚定到 EVM；探测不到锚点文件时跳过，不影响首次运行与单元测试）。不满足返回 409「独立账本比链上锚点更短（本地 N 块 / 锚点 M 块），疑似被截断」。

必须写清的边界：这条检测只能发现「比锚点更短」，**同时改写锚点文件仍可绕过**——锚点与账本在同一台机器上，本实现的信任边界与 `POST /reset` 的说明一致（不宣称单机账本对拥有本机管理员权限的攻击者不可篡改）；EVM 锚定与多副本核对才是它的外部约束。

### 读写路径的性能优化（含两处排障开关）

第六轮做了 5 处优化，原则都是「同样的语义、少得多的往返」：

|优化|原来|现在|
|---|---|---|
|`Crypto.deriveKey` 派生密钥缓存|每解密一行都跑一次 PBKDF2（1000 次迭代）；千级成绩一次解密约 515ms|按 `(password, salt)` 缓存派生结果，上限 4096 条、超限整体清空；热态约 50ms|
|`LedgerService` 两级校验缓存|每次读取都重跑哈希链 + EVM 锚点校验|`localVerified` / `fullVerified` 两级，按「文件大小 + mtime」判定失效，并在所有写入路径显式 `invalidate()`；`/audit` 读取只走本地校验层|
|`/integrity` 批量比对|逐条 `repo.find`；1445 条账本约 2890 次 RPC 往返|一次取回全部成绩在内存比对；批量读取因密文篡改失败时退化为 `verifyRowByRow()` 逐条定位，语义与优化前一致|
|`/roster`、`/courses` 消除 N+1|重修判定为每个更早教学班各查一次选课；学院/班级名称逐门课查询|课程、选课、成绩各取一次后在内存 join；组织名称用新增的 `OrganizationService.namesInto()` 一次取回整表复用|

两个必须写清的技术细节：

- **密钥缓存不放宽安全边界**：salt 存在密文里，能读到密文就能算出密钥，PBKDF2 在这里提供的是固定工作量而非口令保护；加密路径用随机盐，因此缓存永不命中。缓存上限 4096 条、超限清空，避免长期运行下无界增长。
- **账本缓存不能只靠 mtime**：同一毫秒内的连续写入可能不改变时间戳，因此所有写入路径都显式 `invalidate()`，而不是等文件状态变化。

两个默认关闭的排障开关：`-Dcampus.trace.repo=true` 打印每次 `repo.find` 的耗时（定位业务侧往返次数），`-Dcampus.trace.sql=true` 打印每次查询/解密的耗时（定位数据侧耗时来源）。见 [配置说明](configuration.md)。

### 班级名称采用规范编码形式

班级名统一为 `年级-专业-班号`，例如 `2023级-软件工程-2301班`、`2024级-会计学-2401班`，由 `OrganizationService.className(gradeYear, majorName, number)` 生成，演示数据的班级全部遵循该形式（第一轮 6 个，第二轮扩充为 16 个）。

好处是名称本身携带了年级与专业，成绩单、名单、选课范围这些只拿到班级名的场景不需要再联表；同时 `OrganizationService.displayName` 从「拼年级前缀」退化为直接返回 `name`（班级名已经是完整显示名），少一处拼接就少一处不一致。代价是重命名专业或年级时需要同步改班级名，而名称又受 `classes(major_id,name)` 唯一索引约束；演示数据在重建时一次性写好，管理员维护时需要注意这一点。

改动涉及的四个位置：

|受影响的位置|调整|
|---|---|
|`CourseService.saveCourse`|删除新增课程时的 `(code, term)` 唯一性校验|
|`SelectionService.codeHistory`|承担「同一学生不得重复修读同一课程代码」的全部判定|
|前端课程维护|不再因课程代码重复被拒绝，改为在选课页按 `reason` 提示不可选|
|演示数据|仍保持同一学期不重复课程代码（端到端脚本会校验初始化数据的这一性质）|

### 组织编号直接用主键 `id`（第三轮放弃单独的显示编号）

第二轮曾经在可读主键之外再加一个「两位数字显示编号 `code`」（`01`、`02`…，同层唯一、自动生成、不可修改，保存响应里额外带一个「编号不可修改」的布尔标记，前端有一个只读编号输入框）。第三轮把它整体撤掉：组织编号回归主键 `id`，`OrganizationService` 删除 `nextCode`/`maxCode`/`codeOf`，`OrganizeRoutes` 的 `/organizations`、`/organizations/options` 不再输出 `code`（用 `copy.remove("code")` 兜底），`POST /organizations/save` 的响应简化为 `{ok: true, id}`，前端表单里的「编号」输入框彻底删除、列表改为在名称下方显示主键。

放弃的理由是**收益不抵认知成本**：

- 主键 `id` 本身就是可读编号（`C01001`、`M01001`、`B01001`，层前缀区分层级、2 位号段表示上级、3 位序号表示同级次序），页面上再显示一个 `01` 并不能提供额外信息，反而出现「同一行两个编号」的疑问；
- 两套编号的语义差别需要额外解释：`code` 是**同层**唯一、每层从 `01` 重新开始，`id` 是**全局**唯一、带号段——沟通时必须带层级语境（`C01001` 与 `M01001` 的 `code` 都可能是 `01`），这在跨学院、跨层级的报表里只会增加歧义；
- 维护第二套编号要有生成 + 复核逻辑（`findOne` 查空位、`99` 上限、历史脏数据处理），前端还要多一个只读字段与提交时的忽略分支，而这些都建立在「主键不可读」这个并不成立的前提上。

代价与边界：`colleges`/`majors`/`classes` 表里第二轮的 `code` 列**没有删除**——删列会再触发一次结构版本迁移与整库重建，而它已无业务含义，保留的成本只是表里多一个不读不写的列；该列也没有唯一索引，因此不会被误当编号使用。另外，主键编号取「现存最大值 + 1」，删除序号最大的对象后该编号会被再次分配，所以编号不保证永不复用，历史引用以审计快照为准。

### 导航栏宽度改为鼠标拖动调节（第三轮取代折叠按钮）

第二轮给侧栏加的是「折叠/展开」两档按钮（完整宽度 ↔ 仅图标窄栏）。第三轮改为**鼠标拖动自由调节**：侧栏右边缘是一个 `.sidebar-resizer` 拖拽手柄（`role="separator"`、带 `aria-valuenow`/`aria-valuemin`/`aria-valuemax` 与「拖动调节导航栏宽度，双击恢复默认」提示），宽度范围 68–420px、默认 216px；`<118px` 自动进入仅图标档（隐藏文字、保留 `title`/`aria-label`），118–167px 为紧凑档（仍显示文字、收紧内边距）；宽度写入 `localStorage.campus.sidebarWidth`，刷新后保持，双击手柄恢复默认并清除持久化值。

选拖动而不是继续留两档按钮，原因有三点：其一，身份行加上「学院 · 专业 · 班级」之后文字长度差异很大（管理员只有角色、学生有四段），固定两档总有人嫌窄或嫌宽，拖动让用户自己找到合适的宽度；其二，布局上只需一个 CSS 变量——`.app-shell { --sidebar-width }` 同时驱动侧栏宽度与主内容左边距（`max-width: 1150px` 时默认降为 180px），拖动时只改这一个值，不会出现两处宽度不同步；其三，两档按钮要维护两套 class 与两个状态，而拖动只需要一个数值。

为了避免「拖坏」，保留了两条兜底：宽度被夹在 68–420px 之间，拖到最小值也不会出现负宽或横向滚动条；双击手柄一键回到 216px 并清除 localStorage，用户不需要靠清缓存恢复。小屏（`max-width: 760px`）侧栏本来就是横向导航条，因此隐藏手柄。代价是拖动是纯前端显示偏好、不进后端，换浏览器或清空 localStorage 后会回到默认宽度——这符合「显示偏好」的定位，也意味着它不影响权限与任何请求内容。

### 管理员不归属任何组织

第一轮把 `ADMIN` 当成「至少要有学院」的角色，种子数据也给管理员填了学院——但管理员的权限是全局的（`GRADE_ADMIN`、`USER_ADMIN`、`AUDIT`、`ORG_ADMIN`、`SELECTION_ADMIN` 都作用于全校），给他一个学院既没有业务含义，又会让「按学院统计人数」「组织成员列表」这类查询出现一类不好解释的行。第二轮改为：管理员的三级组织字段必须为空，`AdminService.saveUser` 对带组织的管理员请求直接 400，保存时写空串；`OrganizeRoutes.assign` 命中管理员时报 400；`/me` 对管理员返回 `null` 名称，前端身份行只显示「管理员」。

这带来一个连锁效果：按组织字段筛选的查询天然不会返回管理员，因此「组织成员里有管理员」这种数据只可能来自脏数据。为了让这类脏数据不再静默存在，`DemoInitializer.verifyOrganizationIntegrity()` 在灌数结束时逐行校验，其中一条就是「管理员不得带组织」，不合法直接抛异常中止启动。代价是 `users` 表的 `college_id`/`major_id`/`class_id` 出现了「三列全空」这一合法状态，任何新的按组织读取的代码都必须能接受空值（`CoreRoutes.me` 已经做了空值判断）。

### 选课入口合并为一个「选课管理」页面

第一轮管理员侧栏有两个选课相关入口：「课程与选课」（`key = courses`）与「网上选课」（`key = selection`），而两者内容确有重叠——课程列表决定「有哪些课可上」，批次列表决定「哪些课可以被选」。第二轮把它们合并为一个「选课管理」页面（`key = selection`），页内用 `adminSelectionTabs` 分「课程与选课 / 选课批次 / 选课记录」三个标签页；学生的「网上选课」入口与选课台不变。

选择「一个页面 + 标签页」而不是「保留两个入口 + 互相跳转」，是因为这三个标签共享同一批数据语境（同一批课程、同一批批次、同一批流水），跨页面跳转会让管理员在发布批次时反复丢失筛选状态；同时合并后管理员侧栏从 7 项（课程成绩、统计分析、人员与权限、课程与选课、安全审计、组织管理、网上选课）降到 6 项，「安全审计」也顺势被放到最后一项，导航顺序与使用频率一致。代价是 `SelectionView.vue` 现在要同时服务「学生选课台」与「教务批次/记录」两种视角，组件内按角色分支的代码变多了一点——这是为减少入口数量付出的复杂度，与「前端外壳只是展示层」的定位一致。

### 批量选课并入课程界面（按课程维护名单）

第一轮的「批量选课」是独立界面，操作维度是「先选批次、再选班级」。第二轮改为按**课程**操作：每门课程行上的「选课」按钮打开弹窗，可勾选一个学生、多个学生或某个班级的全部学生（并集去重），提交 `POST /enrollments/batch`。这样入口与被操作对象在同一行上，管理员看着课选人，不需要先在批次里回忆起这门课属于哪个批次。

实现上刻意复用选课域已有的能力而不是新写一套：`SelectionService.batchByCourse` 与本轮之前的 `batch` 共用 `enrollments` 的唯一索引处理（已退课的行只能 `UPDATE`）、同一张 `enrollment_records` 流水表与同一组 `ADMIN_ASSIGN`/`ADMIN_REMOVE` 动作；同时把「个别学生不满足规则」表达为返回值里的 `failed[]` 而不是异常，避免一个学生让整批失败。`publishId` 支持自动解析（按课程学期找包含该课程的 `OPEN`、其次 `CLOSED` 批次），因为在课程界面操作时管理员通常并不关心批次编号；找不到批次就留空，流水照样可查。

代价是这条路径不受批次开关与时间窗口约束（教务代选本来就是窗口外的授权操作），所以它的边界只能由 `GRADE_ADMIN` 权限与审计账本承担；批次维度的 `POST /selections/batch` 因此保留，两者在审计里用不同 action（`SELECTION_BATCH` 与 `ENROLLMENT_BATCH`）区分。另一个代价是独自维护名单的入口变多（单人 `/enrollments`、按课程批量 `/enrollments/batch`、按批次批量 `/selections/batch`、学生自助 `/selections/select`），因此三者都写同一张流水表，避免「哪条路径改的名单」在数据上不可追。

### 演示库重建时同时清空独立账本与链锚点

`SchemaCatalog.SCHEMA_VERSION` 变化会删除全部业务表并重灌演示数据。此时独立账本里保存的还是**已删除成绩行**的快照，`/integrity` 会把它们全部判成缺失，因此重建必须连带处理审计侧：`DemoInitializer.resetLedger()` 调用审计服务的重置接口，`LedgerService.reset()` 先调用 chain-worker 的 `POST /reset` 清空 EVM 锚点，再清空本机账本文件。

顺序不能颠倒：旧锚点与新链毫无关系，若账本已清空而锚点仍在，重新锚定会因 `Anchor conflict`（同一下标出现不同哈希）失败。链锚点清除失败时只打印日志并继续重建账本，因为「账本与数据库一致」比「链上锚点连续」更关键。

安全上必须明确：**`POST /reset` 只适用于本机演示重建**，它让账本可以被合法清空，因此生产环境不得暴露该端点（chain-worker 的注释里也写明了这一点）。这也是本实现不能宣称「账本不可被本机管理员重置」的原因，与安全章节的信任边界一致。

### 选课范围用逗号分隔的组织编号列

`course_selections` 的 `scope_college_ids`/`scope_major_ids`/`scope_class_ids` 是逗号分隔字符串，不是关联表。范围是「一组编号」的集合语义，只做包含判断，不需要按范围反向检索；`OrganizationService.split`/`inScope` 解析后判定，空集合即「不限」。代价是无法用 SQL 直接 join 范围，且 `SchemaCatalog.sqlType` 会把 `_ids` 结尾的列建成大文本类型。

### 数据库初始化用整库重建而非增量迁移

`SchemaCatalog` 启动时比对 `schema_meta` 里的标记与 `SCHEMA_VERSION`：不一致就删除全部业务表后按目标结构重建，再由 `DemoInitializer` 重灌演示数据；一致时只补缺表、缺列。**标记是 `结构版本:密钥指纹` 整串**（不是单纯数字）：把密钥指纹一起落库以后，「换了密钥」与「结构升级」走同一条重建路径——两者都会让旧密文失效，提前重建比运行到读某一行时才报完整性失败更好。

选整库重建的直接原因是 H2 在 `CHECK` 表达式变更时会保留旧的命名约束，加列无法修复；同时演示库的全部内容都是可再生的合成数据，重建比维护一套迁移脚本更可靠，也能保证「结构版本」与「演示数据形状」永远一致。代价非常明确：重建会丢弃全部业务数据，并同步清空独立审计账本（旧快照指向已删除的成绩行，见 `resetLedger`）。因此结构版本只在确实无法补列兼容时提升，生产部署必须改用迁移管理工具而不是打开这个开关。

### 整库加密选在文件层而不是再加密若干列

数据服务默认开启 H2 的 `CIPHER=AES`，让**整个 `.mv.db` 文件**成为密文。另一种做法是继续只做字段级加密（现在的 `grades.payload`/`audits.payload` 就是 AES-GCM），但那样账号表、BCrypt 哈希、选课关系、课程代码在磁盘上仍是明文——库文件被拷走或备份卷泄露时这些内容直接可读，而「成绩隐私」的泄露面显然不止分数列。两者并不互斥：现在是文件层整库加密 + 字段层 AES-GCM 两层，前者防离线读取，后者把密文绑定到身份、状态与版本，能识别整行回放与版本回退。

代价有三条，都已写进文档而不是藏起来：① H2 的 AES 实现是 AES-128；② 会话口令必须是「文件口令 + 空格 + 用户口令」两段式，一旦中间的空格被环境变量、启动参数或 shell 吞掉，H2 只报 `Wrong password format ... [90050-224]`，所以 `DataSourceConfig` 改为显式取值并让日志打印「来源 + 长度 + 空格数」；③ 开启加密后旧的明文库打不开（H2 会报 `File corrupted while reading record`），因此 `DatabaseBootstrap` 在 Spring 之前按文件头（加密库 `H2encrypt`、明文库 `H2:`）识别并清理。另外要讲清信任边界：整库加密保护静态文件，不保护运行中的进程——库文件与 `secrets.json` 同机可读时，本机管理员仍能解密。

### 密钥与口令动态生成，而不是读写进配置文件

课程要求原文第 17 页明确「禁止硬编码密钥 / 密码」，而此前的实现把 6 个 `*_KEY` 默认写成字面量 `KEY`、把 TLS 口令固定为 `campus-dev-tls-2024`——等于把凭据写进了版本库。现在的做法是：`scripts/setup.mjs` 用 `crypto.randomBytes(32)` 生成 9 项密钥写入 `.runtime/secrets.json`（0600、`.gitignore` 忽略），yml 里一律是空占位 `${VAR:}`，启动脚本把 9 项**同时**作为环境变量与 `-D` 启动参数注入，`ConfigGuard` 与 `ConfigEnvironmentPostProcessor` 保证在数据源建立之前就绪，`chain-worker` 也从环境变量或密钥文件读取、缺失即退出。

选择「密钥文件 + 注入」而不是「每次启动随机生成」：后者会让四个独立进程与 Node 进程各拿到不同的值，签名互不通过，且重启一次就丢掉全部历史密文的可解密性。选择「生产档拒绝启动」而不是「打日志警告」：警告在运维脚本里会被忽略，而缺密钥时系统本来也跑不起来——把失败提前到启动最早期并打印缺失清单，比运行到第一次内部调用才报 401 更省事。这个方案的已知弱点也写进了安全文档：便利模式下四个进程共用一份密钥表，任一进程被攻陷即可读到全套密钥；生产应改为 KMS/Vault 或按进程只发需要的密钥，并接受「换密钥 = 整库重建」这一后果（`schema_meta` 的密钥指纹会失配）。

### 领域路由注册表代替单一 dispatch switch

新增 `Routes` 接口，每个领域服务（`CoreRoutes`、`OrganizeRoutes`、`SelectionRoutes`）声明自己处理的路径集合，`ApiController` 只做信封解析、会话/CSRF 校验、403 审计与分页，然后按 `handles()` 把请求交给唯一匹配的实现。

原来的单函数 `switch` 在加入组织和选课后会变成一处所有人都要改的代码；拆成注册表后，新增业务域不需要修改既有分发代码，每个域的读写分支也能各自独立测试。代价是路径集合可能重叠——`Set.of` 不检查跨实现重复，出现重复时按 Spring 注入顺序命中第一个实现，这一点依赖代码审查而不是运行时校验。

## 实测问题与修复

- 发现返回 URL 的 Spring String 响应并非 JSON 字符串，注册发现改为 `{url: ...}` 对象契约。
- 将自签名私钥 PKCS12 用作信任库导致 trustAnchors 错误，改为独立证书 truststore。
- EVM 数据库重启后随机测试账户失去原有余额，改为稳定测试账户与本机测试 gas 初始化。
- CSP 阻止 OCR WebAssembly，增加仅允许 WASM 编译的 `wasm-unsafe-eval`，并允许本地 blob 读取，保留对任意脚本 eval 的限制。
- 停用学生从课程退选被启用状态检查错误阻止，调整为新选课必须启用，退选允许已停用学生，但仍禁止删除已有成绩的选课关系。
- 前端 Vite、Playwright、node-forge 审计有漏洞，升级到修复版本并锁定依赖。
- Ganache 捆绑依赖无法全部通过兼容更新消除漏洞，保留上游审计结果并限定本机教学运行，不伪造“全依赖零漏洞”结论。
- 开发重打包会影响在途 JAR 类加载，启动器改为每次复制独立不可变运行 JAR；最终浏览器草稿保存与重载回归通过。
- 使用 Path.toUri 发布静态目录，Java 源清单统一路径分隔符，keytool 使用参数数组直接执行，避免带空格路径和 Windows 分隔符问题。
- 端到端脚本第一次运行 108/112：`CourseService.saveCourse` 的 `(code, term)` 唯一性校验使「不同教师开设同一门课」无法验收（4 条失败全部在此）。移除该校验、把重复修读判定移到选课环节后重跑 111/111。
- 演示库重建后重新锚定失败（`Anchor conflict`）：新增 chain-worker `POST /reset`，由 `LedgerService.reset()` 在清空账本前先清空 EVM 锚点。
- PowerShell 会拆坏 `-Dcampus.reset-db=true` 这类参数，Windows 一键启动改用 `scripts/start.ps1`，以参数数组直接调用 `java`。
- 整库加密开启后 `start.ps1` 写进 `.logs/jvm.args` 的两段式 `-DDB_PASSWORD` 被 JVM 的 argfile 解析器按空白拆成两个参数，第二个被当成主类（`ClassNotFoundException`）。修法是给该行加引号（`'"-DDB_PASSWORD=' + $dbPassword + '"'`），本机实测启动日志里口令形态为「长度 129、空格数 1」。
- 文档复查时发现一个容易写错的细节：长度校验**只在生产档生效**。`ConfigGuard.load()` 的判据是 `production && (PLACEHOLDERS.contains(value) || value.length() < MIN_LENGTH)`，因此生产档下「值 < 16 字符」会拒绝启动，而开发档若手工注入了一个短值（如 `GATEWAY_KEY=my-dev-secret`）会被直接采用——开发档的兜底只负责「缺失时生成」，不负责「太短时替换」。因此文档里给出的手工注入示例一律使用 64 位十六进制，而不是随手编一个短口令。
- **（第二轮）48 名学生的 `college_id` 被写成专业编号**：`DemoInitializer` 用 `find(CLASSES, classId).parent()` 取学院，而 `Org.parent()` 返回的是上一级编号——班级的 parent 是专业，于是所有学生的 `college_id` 都是 `M01xxx` 这类专业编号。后果很隐蔽：列表页看不出异常，但选课范围校验（`inScope` 比较 `college_id`）永远不通过，学生选课一律 403「你不在此次选课范围内」。修复是学院一律走「专业 → 学院」反推（`major.parent()`），并新增 `DemoInitializer.verifyOrganizationIntegrity()` 在灌数结束时逐行校验三级归属与「管理员无组织」，不合法直接抛异常中止启动，让同类问题不可能再静默入库。
- **（第二轮）登录后的身份行没有组织信息**：`App.vue` 的 `login()` 用 `POST /login` 返回的 user（只含 `id`/`username`/`name`/`role`/`permissions`），而 `collegeName`/`majorName`/`className` 只有 `GET /me` 才返回，因此「登录后立刻看身份行」与「刷新页面后看身份行」结果不同。修复是登录成功后立即补一次 `api("/me")` 再进入应用初始化，身份行在两种路径下一致；浏览器检查里专门加了「教师/学生身份含学院、专业、班级」与「管理员不含组织、不出现 null」的断言。
- **（第二轮）`SchemaCatalog.wasRebuilt()` 语义错误**：空库首次建表时它同样返回 `true`，把「新建库」误报成「丢弃了已有数据」，初始化日志与 `DemoInitializer` 的判断都会因此产生误导。修复为只有「库里原有业务数据、且因结构版本不匹配被删除」时才返回 `true`，并新增 `hasBusinessRows()` 做判定；`SchemaCatalogTest` 增加了结构版本过期重建与补列迁移两条回归用例。
- **（第四轮）`Models.total` 对系数表缺项抛异常，导致重修判定静默失效**：原实现对缺失的权重项执行 `number(null)` 抛 NPE，而重修判定的两个入口（`SelectionService.failedCodes`、`CourseService.failedCodesBefore`）都用 `catch (RuntimeException ignored)` 兜底，于是课程行 `weights` 不全时挂科学生不会被判定为重修——教师端名单与学生端徽标同时失效，且没有任何日志。修复为**缺失系数按 0 权重处理**：缺项只是不参与计算，不会把整门课变成「无成绩」；`ModelsTest` 补充了该分支的用例。这条同时消除了一处「异常被吞掉后无迹可循」的静默失败点，也是本轮把重修判定做成派生值后新增的健壮性要求。
- **（第五轮）`AnalyticsService.predict` 的预测对象筛选条件写反，学业预警永远没有结果**：筛选「期末未考、可用于预测」的学生时写成了「跳过期末未录入的人」，把真正要预测的对象全部排除，于是接口返回 200、`results` 却是空数组，页面上看不到任何预测行（用户看到的只有「数据不足」这类提示）。修复为 `regular != null && lab != null && finalExam == null` 才进入预测；`AnalyticsRulesTest` 补了「预测返回缺期末的学生」与「历史不足 422」两条用例。数据侧同时补了历史样本层与缓考样本池，并把启动自检升级为 `verifyPredictionCoverage()`——这类「接口成功但结果为空」的缺陷不会抛异常，只能靠断言覆盖返回内容来发现。
